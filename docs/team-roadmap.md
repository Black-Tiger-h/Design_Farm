# Design_Farm — 코딩 입문자 3인 개발 로드맵

작성일: 2026-09-18 · 기준: [기능명세서](functional-spec.md)

목표는 모든 기술을 먼저 공부하는 것이 아니라, 작은 기능을 만들고 연결하면서 필요한 기초를 익히는 것이다. 아래 역할은 주 담당이며 서로의 코드를 전혀 모르는 분업을 뜻하지 않는다.

현재 저장소는 HTML 프로토타입이다. Next.js·FastAPI·Supabase 프로젝트는 아직 구현되지 않았다. 현재 앱은 [README의 실행 방법](../README.md#실행하기)으로 확인한다.

## 1. 역할과 첫 결과물

| 담당 | 책임 | 처음 만들 결과물 | 뒤에 맡을 기능 |
| --- | --- | --- | --- |
| A — 프런트엔드 | 사용자가 보는 화면과 조작 흐름 | 예시 작품 3개를 보여주는 작품 카드 목록 | 검색·공간 필터, 로그인 화면, 등록·입찰 화면, 프로필·요청함 |
| B — 인증·경매 백엔드 | 누가 무엇을 할 수 있는지와 입찰 규칙 | 서버 상태를 알려주는 API와 자동 검사 1개 | 인증·권한, 동시 입찰·마감·낙찰, 거래 상태, 보안 검증 |
| C — 전시·커리어 백엔드 | 작품·작가·요청 데이터를 저장하고 제공 | 예시 작품 3개를 반환하는 API | 작품·프로필·이미지·관심 작품, 순위, 스카우트·외주 요청 |

B가 보안 커리어를 준비하는 역할이다. 다만 인증과 경매는 어려운 부분이므로 Python·HTTP·DB 기초 이후에 진행한다. 보안 책임은 세 명이 함께 지며 B는 공통 기준과 검증을 주도한다.

## 2. 일정 잡는 법

아래 6단계를 순서대로 진행한다. 달력보다 **완료 기준을 통과했는지**로 다음 단계 진입을 결정한다. 첫 주에 각자의 실제 학습·개발 시간을 기록한 뒤 팀 일정을 정한다. 아직 숙련도와 가용 시간이 없으므로 출시 날짜를 확정하지 않는다.

| 단계 | 팀이 만드는 결과 | 다음 단계 진입 조건 |
| --- | --- | --- |
| 0. 공통 입문 | 세 명 모두 현재 시안을 실행하고 작은 수정 제출 | 수정 이유·결과·되돌리는 방법을 설명할 수 있음 |
| 1. 언어·도구 기초 | A 작품 목록, B 상태 API, C 작품 목록 API | 각자 본인 코드의 입력→처리→출력을 설명할 수 있음 |
| 2. 첫 연결 | 브라우저에서 서버 작품 3개 조회 | A 화면이 C API 응답을 보여주고 실패 시 오류 표시 |
| 3. 데이터·계정 | 로그인한 작가의 작품 등록과 다른 회원의 조회 | 새로고침 후 데이터 유지, 타인 작품 수정 차단 |
| 4. 경매 | 여러 테스트 계정의 입찰·마감 결과 | 동시 입찰·단독 낙찰·마감 후 거절 검사 통과 |
| 5. 커리어·통합 | 포트폴리오·테스트 순위·협업 요청 | 등록→탐색→입찰→결과→협업 요청을 세 명이 재현 |

실결제·정산·실제 학생 인증은 이 학습 로드맵 다음 단계다. 디지털 작품은 전시와 테스트 경매까지만 다루며 판매 정책을 임의로 확정하지 않는다.

## 3. 처음 5회 모임 — 모두 함께

한 회에 끝내지 못하면 같은 과제를 다음 모임에 이어 한다.

| 회차 | 할 일 | 남길 결과 |
| --- | --- | --- |
| 1 | 저장소 복제, 에디터에서 폴더 열기, 현재 앱 실행. 구매자·작가 흐름을 직접 클릭 | 각자 실행 화면과 이해되지 않는 용어 5개 |
| 2 | 파일·폴더·터미널·명령어 익히기. HTML 제목 또는 안내 문구 한 곳 수정 | 변경 전후 차이를 설명하는 작은 커밋 |
| 3 | Git의 변경 확인·커밋·브랜치·push·PR·리뷰 흐름 연습 | 각자 기능 브랜치에서 문서 수정 PR 하나 |
| 4 | 브라우저 개발자 도구의 Console·Network 열기. HTTP 요청·응답, JSON 예시 읽기 | 작품 한 점을 JSON으로 표현한 공통 예시 |
| 5 | 역할별 작은 과제 착수. 결과를 서로 실행해 보기 | A 카드 1개, B Python 함수 1개, C 작품 목록 데이터 1개 |

설치 대상은 공통 Git·에디터, A는 Node.js, B·C는 Python이다. Supabase 프로젝트와 환경변수는 3단계 진입 때 함께 설정한다. 정확한 런타임·패키지 버전은 프로젝트 생성 시 정하고 저장소에 고정한다. 팀원이 각자 다른 튜토리얼 버전으로 프로젝트를 만들지 않는다.

### 자주 만나는 용어

| 용어 | 이 프로젝트에서의 의미 |
| --- | --- |
| 프런트엔드 | 작품을 보여주고 버튼·입력창을 제공하는 브라우저 화면 |
| 백엔드 | 작품을 저장하고 입찰 가능 여부를 판단하는 서버 |
| API | 화면과 서버가 데이터를 주고받기로 약속한 주소·입력·응답 |
| JSON | 작품명·가격 같은 데이터를 주고받는 형식 |
| DB | 새로고침해도 없어지지 않게 데이터를 저장하는 곳 |
| 인증 / 권한 | 누구인지 확인 / 그 사람이 해당 작업을 해도 되는지 확인 |
| PR | 내 변경을 다른 팀원이 확인하고 합치도록 요청하는 단위 |
| 마이그레이션 | DB 구조 변경을 파일로 기록해 같은 순서로 적용하는 방법 |
| 트랜잭션 | 여러 DB 처리를 함께 성공시키거나 함께 취소하는 작업 단위 |

## 4. A — 프런트엔드 로드맵

학습 순서: **HTML·CSS → JavaScript → TypeScript 기초 → React → Next.js → API 연결**.

| 단계 | 배울 것 | Design_Farm 실습 | 완료 기준 |
| --- | --- | --- | --- |
| A1 | HTML 구조, 폼·라벨, CSS 여백·배치, 모바일 대응 | 제목·작가·크기·공간 안내가 있는 작품 카드 1개 | PC와 360px 화면에서 내용이 잘리지 않고 링크·버튼을 키보드로 사용 |
| A2 | 변수, 함수, 배열·객체, 조건문, 이벤트, `map`·`filter` | 예시 작품 3개 표시, 공간 선택으로 필터링 | 서재 선택 시 서재 작품만 표시, 결과 없을 때 안내 |
| A3 | TypeScript 객체 타입, React 컴포넌트·props·state | 작품 목록·카드·검색 입력을 React로 구성 | 검색어 변경으로 목록이 갱신되고 각 데이터의 타입 설명 가능 |
| A4 | Next.js 페이지·동적 경로, 서버/클라이언트 역할, 비동기 요청 | `/artworks`와 작품 상세 연결, C의 API 호출 | 로딩·성공·빈 목록·오류 네 상태를 구분 |
| A5 | 로그인 상태, 폼 검증, 업로드 진행·실패, 보호 화면 | 로그인·등록·관심 작품·내 활동 화면 | 서버 저장 성공 후만 성공 안내, 오류 시 입력 유지 |
| A6 | 변경 중인 데이터 처리, 확인창, 접근성 | 입찰 확인·가격 변경 안내·요청함 | 가격이 바뀌어도 자동으로 금액을 올려 제출하지 않고 재확인 |

처음에는 기존 미술관 스타일과 예시 이미지를 재사용한다. 디자인을 새로 만들면서 프레임워크까지 동시에 배우지 않는다. 전역 상태 라이브러리·복잡한 애니메이션은 현재 기능에 필요해진 뒤 검토한다.

**첫 작업 카드:** “예시 작품 3개를 카드로 표시하고 서재 필터를 붙인다.” 입력은 로컬 배열, 결과는 화면이다. 로그인·DB·실제 경매는 이 카드에 넣지 않는다.

## 5. B — 인증·경매·보안 로드맵

학습 순서: **Python → HTTP·FastAPI → SQL·DB → 인증·권한 → 경매·트랜잭션 → 보안 검증**.

| 단계 | 배울 것 | Design_Farm 실습 | 완료 기준 |
| --- | --- | --- | --- |
| B1 | Python 변수·함수·조건문·리스트·딕셔너리·예외, 가상환경 | 시작가와 기존 입찰을 받아 최소 입찰가 계산 | 첫 입찰·다음 입찰·잘못된 값의 기대 결과를 작은 자동 검사로 확인 |
| B2 | HTTP 메서드·상태 코드·JSON, FastAPI 경로·입력 모델 | 상태 API, 금액 입력을 검증하는 연습 API | 정상 요청 성공, 잘못된 입력 거절. API 문서에서 직접 실행 |
| B3 | SQL 조회·삽입, 기본키·외래키·제약·트랜잭션 | 테스트 DB에서 계정·작품·경매 관계 읽기 | 어떤 계정의 작품인지 ID로 설명하고 잘못된 참조를 DB가 거절 |
| B4 | Supabase Auth, 토큰 검증, 인증과 권한의 차이 | 로그인 회원 확인, 본인 작품 입찰·타인 수정 차단 | 만료·변조 토큰과 타인 ID 요청 거절. 화면 숨김만으로 보호하지 않음 |
| B5 | 서버 시각, 행 잠금, 중복 방지 키, 상태 전이 | 입찰 저장·동시 요청·마감·낙찰 구현 | 기능명세 AT-08~14 통과, 서버 재시작 후 마감 처리 가능 |
| B6 | 위협 모델, 비밀키 관리, 최소 권한, 로그의 민감정보 | 자기 팀의 로컬·테스트 환경에서 권한·금액·재시도 공격 시나리오 검사 | 문제 재현→수정→재검증 기록. 키·토큰을 Git이나 로그에 남기지 않음 |

Auth의 비밀번호 저장·로그인 기반을 활용하며 암호화·토큰 발급 체계를 직접 만들지 않는다. 인증 성공 뒤에도 작품·거래마다 소유권 검사가 필요하다. FastAPI 입력 검증만으로 동시 입찰 문제가 해결되는 것은 아니므로 DB 단계까지 검증한다.

**첫 작업 카드:** “입찰이 없으면 시작가, 있으면 최고가+1,000원을 반환하는 Python 함수와 검사 3개를 만든다.” 서버·DB 없이 규칙부터 이해한다. 이 연습 함수는 추후 실제 서버 구현에 맞춰 통합한다.

**보안 포트폴리오 산출물:** 보호할 데이터와 접근 주체 표, 권한 검사 테스트, 동시 입찰 재현 기록, 수정 전후 결과. 해결하지 못한 문제도 범위와 재현 조건을 기록한다.

## 6. C — 전시·커리어·협업 로드맵

학습 순서: **Python → HTTP·FastAPI → SQL·데이터 모델 → 작품·파일 저장 → 커리어·요청 API**.

| 단계 | 배울 것 | Design_Farm 실습 | 완료 기준 |
| --- | --- | --- | --- |
| C1 | Python 함수·리스트·딕셔너리·반복문·필터 | 작품 3개에서 공간·종류로 검색 | 입력 조건과 반환 작품을 설명하고 없는 조건에는 빈 목록 반환 |
| C2 | API 경로·매개변수·응답 형식 | 예시 작품 목록·상세 API | A가 같은 API 응답으로 카드·상세 화면을 표시. 없는 ID는 조회 실패 응답 |
| C3 | PostgreSQL 테이블·키·관계·조회, 마이그레이션 | 작가·작품·이미지·관심 작품 저장 | 서버 재시작 후 유지, 같은 관심 작품 중복 저장 방지 |
| C4 | 생성·조회·수정·삭제, B의 인증 기능 사용, 업로드 검증 | 작품 초안·공개·수정, 공간 안내, Storage 이미지 연결 | 소유자만 수정, 비공개 작품 접근 제한, 잘못된 파일 거절 |
| C5 | 집계 쿼리·상태별 조회·정렬 | 작가 포트폴리오와 테스트 거래 완료 순위 | 동명이인 분리, 공동 순위 적용, 낙찰만 된 거래 제외 |
| C6 | 발신자·수신자 권한, 요청 상태·중복 방지 | 스카우트·외주 요청, 받은함·보낸함 | 제3자 조회 거절, 재시도 중복 없음, 수락·취소 충돌 처리 |

B의 경매 상태 정의가 확정되기 전에는 실제 순위 집계를 먼저 만들지 않는다. 승인한 테스트 데이터를 사용해 화면 응답 형식부터 맞춘다. 파일 확장자 검사만으로 업로드 검증을 끝내지 않는다.

**첫 작업 카드:** “작품 3개를 JSON으로 반환하는 목록 API를 만든다.” DB 없이 응답부터 합의하고, 화면 연결에 성공한 뒤 DB로 바꾼다.

## 7. 세 역할을 연결하는 첫 기능

처음부터 홈·로그인·경매 전체를 나누어 만들면 서로 기다리게 된다. 먼저 **작품 목록 하나를 끝까지 연결**한다.

1. 세 명이 작품 응답에 필요한 이름을 정한다: `id`, `title`, `artist_name`, `category`, `recommended_space`, `size_label`, `image_url`. 이름은 첫 API 설계에서 확정한다.
2. C는 위 형식으로 예시 작품 3개를 반환한다. B는 같은 FastAPI 앱이 실행되도록 도와주고 기본 오류 형식을 함께 정한다.
3. A는 같은 예시 데이터로 화면을 먼저 만든 뒤 서버 응답으로 교체한다.
4. 작품 있음·빈 목록·서버 오류를 함께 확인한다. 그다음 C가 저장소를 DB로 바꿔도 화면 응답 약속은 유지한다.
5. 다음 기능은 로그인한 작가의 작품 등록이다. 여기서 B의 인증, C의 저장, A의 폼을 연결한다.

이 흐름이 끝나기 전에는 실시간 기능이나 결제 연동을 시작하지 않는다.

| 영역 | 주 담당 | 함께 확인할 사람 |
| --- | --- | --- |
| `frontend/` 화면·스타일 | A | C가 요청함·프로필 화면부터 보조 가능 |
| `backend/` 공통 인증·경매·거래 | B | C가 DB 제약·상태 전이 리뷰 |
| `backend/` 작품·작가·관심·협업 | C | B가 권한·업로드·개인정보 리뷰 |
| DB 마이그레이션 | B가 적용 순서 취합, 각 기능 담당이 작성 | B·C 함께 검토 |
| API 명세·기능명세 변경 | 변경 기능 담당 | 해당 API를 쓰는 사람과 합의 |

백엔드는 하나의 FastAPI 프로젝트를 사용한다. B·C가 각각 별도 서버·별도 로그인 체계를 만들지 않는다. 패키지 설정·환경변수 예시 같은 공통 파일은 변경 전에 팀에 알린다.

## 9. 매일 작업하는 방법

1. 한 번에 목표 하나만 정한다. “회원 시스템 구현” 대신 “로그인 실패 시 입력 아래에 오류 표시”처럼 작게 쓴다.
2. 필요한 개념 하나를 공부한 뒤 바로 프로젝트에 적용한다.
3. 정상 입력 하나와 실패 입력 하나로 확인한다. 권한·돈·상태 변경은 자동 검사도 남긴다.
4. 변경 이유, 확인한 방법, 남은 문제를 PR에 적는다. 다른 사람이 확인한 뒤 합친다.
5. 막히면 시도한 명령, 기대 결과, 실제 오류, 관련 코드만 공유한다. 비밀번호·키·토큰은 제외한다.

AI에게는 “이 함수의 입력과 출력 설명”, “오류 원인 후보”, “이 변경의 실패 사례”처럼 좁게 요청한다. 생성된 코드를 실행해 보고 본인이 설명할 수 있어야 합친다. 이해되지 않는 큰 변경은 작은 기능으로 다시 나눈다.

매주 한 번은 최신 코드를 새로 받아 세 명이 함께 실행한다. API 담당자의 컴퓨터에서만 성공한 상태를 완료로 보지 않는다. 코드 리뷰에서는 스타일보다 동작·권한·실패 시 데이터 보존을 먼저 확인한다.
