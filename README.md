# Design_Farm

**예술대학생의 작품과 다음 기회를 연결하는 온라인 미술관.**

중간·기말 평가를 위해 만든 작품이 새로운 공간과 사람을 만날 수 있도록, 작품 감상부터 경매 참여와 작가 협업 제안까지 연결합니다. 구매자는 작가가 직접 소개한 작품의 크기, 어울리는 공간, 배치 방법을 참고해 취향에 맞는 작품을 찾습니다.

현재는 **구매자와 학생 작가 양쪽의 화면 및 사용 흐름을 확인하는 HTML 프로토타입**입니다. 여백과 작품 중심의 미술관 분위기로 구성했습니다.

## 실행하기

별도 패키지 설치나 빌드 없이 `index.html`을 브라우저로 열 수 있습니다.

로컬 서버를 사용하려면 Python 3가 설치된 환경에서 다음 명령을 실행하세요.

```sh
git clone https://github.com/Black-Tiger-h/Design_Farm.git
cd Design_Farm
python3 -m http.server 4173 --bind 127.0.0.1
```

브라우저에서 <http://127.0.0.1:4173>에 접속합니다. 수정한 화면이 보이지 않으면 페이지를 새로고침하세요. 서버 종료는 `Ctrl+C`입니다.

## 주요 기능

| 영역 | 체험할 수 있는 기능 |
| --- | --- |
| 작품 전시 | 실물·디지털 작품 감상, 작품·작가 검색, 종류별 필터, 정렬, 관심 작품 |
| 공간 제안 | 작품 크기·재료 확인, 어울리는 공간별 필터, 작가가 작성한 배치 안내 |
| 경매 | 시작가 및 입찰 이력 확인, 입찰, 마감 결과 체험 |
| 작품 등록 | 이미지와 작품 정보, 시작가, 추천 공간 및 배치 방법 입력 |
| 작가와 커리어 | 시안용 낙찰 건수에 따른 순위, 작가 소개 및 작품 목록 |
| 협업 제안 | 스카우트·외주 요청 양식 작성, 내 활동에서 요청 확인 |
| 내 활동 | 참여한 경매, 등록한 작품, 보낸 요청과 내 작가에게 온 요청 확인 |

### 둘러보기 순서

1. **작품 둘러보기**에서 공간을 선택하고 작품 상세의 크기와 공간 제안을 확인합니다.
2. 작품에 입찰한 뒤 **내 활동 → 마감 결과 체험**으로 낙찰 흐름을 확인합니다.
3. **작품 등록**에서 학생 작가의 등록 과정을 체험합니다.
4. **작가와 커리어 → 작가와 작품 보기**에서 스카우트 또는 외주 요청을 작성합니다.

## 경매와 순위 기준

- 학생 작가가 시작가를 정하며, 첫 입찰은 시작가부터 가능합니다.
- 입찰 금액은 1,000원 단위이고, 다음 입찰은 현재 최고가보다 최소 1,000원 높아야 합니다.
- 한 명만 시작가에 입찰해도 해당 금액에 낙찰됩니다. 입찰이 없으면 유찰됩니다.
- 예상 가격대는 1만~10만 원이며, 입찰 상한을 뜻하지 않습니다.
- 작가 순위는 시안용 낙찰 건수를 기준으로 합니다. 진행 중인 입찰과 유찰은 포함하지 않으며, 동률은 같은 순위를 부여합니다.

## 프로토타입 범위

작품·작가 정보와 초기 거래 실적은 예시입니다. 입찰·등록·관심 작품·요청은 현재 페이지의 메모리에서만 관리되어 **새로고침하면 초기화**됩니다.

로그인, 학생 인증, 서버·데이터베이스, 실제 결제·정산·배송은 구현하지 않았습니다. 스카우트·외주 요청은 실제 상대에게 전달되지 않습니다. 순위는 검증된 경력이나 실제 거래 실적을 의미하지 않습니다.

디지털 작품의 판매 횟수, 독점 여부와 이용 조건은 추후 결정할 사항입니다.

## 현재 기술 구성

HTML, CSS, JavaScript와 내장 SVG 예시 작품으로 구성되어 있습니다. 프런트엔드 프레임워크나 외부 패키지를 사용하지 않습니다.

```text
index.html       화면, 스타일, 예시 작품, 경매·커리어 로직
check.cjs        경매 및 작가 순위 로직 검사
docs/            제품 기획서
```

## 검사 실행

Node.js 18 이상에서 별도 의존성 설치 없이 실행합니다.

```sh
node check.cjs
```

시작가, 최소 입찰 증가액, 잘못된 금액, 단독 입찰 낙찰, 유찰, 마감 이후 입찰 차단 및 작가 순위 집계를 검사합니다. 화면 전체를 자동 검사하는 테스트는 아닙니다.

## 향후 개발 계획

**승인된 개발 구성: Next.js + TypeScript / FastAPI + Python / Supabase.** 아래 내용은 앞으로 구현할 계획이며, 현재 저장소는 HTML 프로토타입입니다. 위의 실행 방법은 현재 프로토타입 기준입니다.

### 기술 선택과 역할

| 구성 | 담당 역할 | 선택 이유 |
| --- | --- | --- |
| Next.js + TypeScript | 작품 전시, 검색, 작가 프로필, 등록·입찰·협업 요청 화면 | 작품·작가별 페이지를 구성하고 데이터 형식을 명확히 관리한다. |
| FastAPI + Python | 작품·경매·거래·순위·협업 요청 API와 권한 검증 | 핵심 업무 규칙을 Python 백엔드에 모으고 입력값 검증과 자동 API 문서를 활용한다. |
| Supabase PostgreSQL | 사용자 프로필, 작품, 입찰, 거래, 협업 요청 데이터 | 관계가 있는 데이터를 저장하고 트랜잭션으로 거래의 일관성을 보장한다. |
| Supabase Auth | 회원가입·로그인·인증 토큰 발급 | 인증 기반을 활용하고, FastAPI에서 토큰과 작업별 권한을 검증한다. |
| Supabase Storage | 작품 이미지와 파일 저장 | 파일을 DB 기록과 연결하고 공개 이미지와 접근 제한 파일을 구분한다. |
| 기존 CSS 활용 | 미술관 분위기의 반응형 화면 | 현재 디자인을 유지하며 화면을 단계적으로 이전한다. |

Next.js는 화면을 담당하고 FastAPI는 업무 처리를 담당한다. 경매·순위 규칙을 양쪽 서버에 중복 구현하지 않는다. 입찰과 거래 변경은 FastAPI를 거쳐 처리하며, 브라우저가 DB의 거래 기록을 직접 수정할 수 없도록 권한을 제한한다.

참고: [Next.js 문서](https://nextjs.org/docs), [FastAPI 문서](https://fastapi.tiangolo.com/), [Supabase 문서](https://supabase.com/docs).

### 단계별 개발 순서

| 단계 | 개발 내용 | 완료 확인 기준 |
| --- | --- | --- |
| 1. 기반 구성 | Next.js 화면 이전, FastAPI 연결, DB 스키마·마이그레이션, 로그인·작가 프로필, 환경변수 분리 | 로그인한 사용자 정보가 새로고침 후에도 유지되고, 다른 사용자의 정보를 임의로 수정하려는 요청은 거절한다. |
| 2. 온라인 전시 | 작품 등록·수정, 이미지 업로드, 크기·재료·작가 노트·추천 공간·배치 안내, 검색·필터·관심 작품 | 학생이 올린 작품을 다른 계정에서 찾고 공간 안내까지 확인할 수 있다. 작품 변경은 권한이 있는 사용자만 가능하다. |
| 3. 경매 | 시작가·입찰 단위 검증, 서버 기준 마감, 동시 입찰 처리, 낙찰·유찰 기록 | 동시 입찰에도 최고가가 일관되며, 마감 후 입찰과 자신의 작품 입찰은 거절한다. 단독 입찰은 시작가에 낙찰되고 마감 처리를 재실행해도 결과가 중복되지 않는다. |
| 4. 작가 커리어 | 포트폴리오, 거래 실적 집계, 스카우트·외주 요청 저장 및 수신함 | 요청이 해당 작가에게만 보이고, 순위에 진행 중 입찰·유찰·취소 거래가 포함되지 않는다. 결제 도입 전에는 테스트 실적임을 표시한다. |
| 5. 실거래 준비 | 결제·정산 연동, 배송·수령 확인, 신고·취소·환불 처리, 학생 인증 절차, 디지털 작품 전달 정책 | 낙찰·결제·거래 완료를 구분하고 결제 알림의 중복 수신에도 중복 처리가 발생하지 않는다. 실제 거래 완료 기록을 기준으로 커리어 실적을 집계한다. |
| 6. 배포·사용성 검증 | 프런트·백엔드 배포, 운영 환경 설정, 오류 기록·백업·복구 점검, 모바일·키보드 사용성 확인 | 구매자와 학생 작가가 등록→감상→입찰→결과 확인 및 협업 요청 흐름을 완료한다. |

### 경매 데이터 처리 원칙

- 금액은 원 단위 정수로 저장하고, 최소 입찰가·본인 작품 여부·마감 시간을 서버에서 검증한다.
- 입찰 검증과 기록을 DB 트랜잭션 안에서 처리한다. 같은 경매의 동시 요청은 행 잠금 등으로 순서를 보장한다.
- 서버가 재시작되더라도 마감 대상 경매를 다시 처리할 수 있게 구성한다. 중복 실행으로 낙찰 기록이 늘어나지 않도록 제약을 둔다.
- 작가는 이름이 아닌 고유 ID로 식별한다. 실서비스 순위는 검증된 거래 완료 건수로 집계하며, 시안의 예시 실적과 분리한다.
- 권한 검사, 동시 입찰, 마감 경계, 요청 재시도와 거래 상태 변경을 중점적으로 검증한다.

### 개발 중 별도로 결정할 사항

배포 서비스와 운영 비용, 결제 사업자·수수료·정산 방식, 학생 인증 방식, 배송·환불 정책, 디지털 작품의 판매 횟수·이용 권한은 아직 확정하지 않았다. 각 단계에 착수하기 전에 필요한 정책과 서비스를 결정한다. 일정은 팀 구성과 개발 가능 시간을 확인한 뒤 산정한다.
